- **Status:** Accepted
- **Tier:** Public
- **Date:** 2026-09-20
- **Bead:** `personal-cfo-vlfd`
- **Decider:** Owner, program plan v0.8.1 §9.4 (recorded in the bead before

- **Builds on:** [ADR 0074](0074-dohflow-sync-architecture.md) (compare-and-
  swap and rollback-then-replay), ADR 0027 (additive balance assertions), and
  ADR 0055 (scenario reversal handles)
- **Consumers:** `personal-cfo-egn67` (SYNC-2b), `personal-cfo-0g528`
  (SYNC-2c), `personal-cfo-mpep3` (S3-2), and the two-vault simulator in
  `personal-cfo-tp2ln`

## Context

ADR 0074 makes the server head a compare-and-swap sequence and rebases an
outbox by rolling a scratch vault back to the base image, applying the pulled
tail, and replaying local envelopes whose write sets remain safe. A ledger
mutation cannot use last-write-wins: an apparently disjoint edit can still
violate a posting, reference, or forecast invariant. The rebase therefore
needs a deterministic, per-command rule that says whether an envelope is safe
to apply, needs a human choice, or must be reopened in an editor.

The current command bus already carries the provenance needed to keep a
disposition explainable. `CommandMeta` has the immutable `command_id`, the
logical `correlation_id`, and optional `causation_id` at
`crates/db-worker/src/lib.rs:174-188` (the plan's older
`finance-kernel/lib.rs:176` pointer is now the propagation site, such as
`finance-kernel/src/lib.rs:2503-2505`). A queued child that references a row
created by a queued parent must not be detached from that causal group.

The `WriteCommand` enum had 50 variants (53 after SYNC-2b, Addendum A) at
`crates/db-worker/src/lib.rs:223-698`. Their doc comments are the source for
the four shapes below. The three hard-delete implementations are explicit
`DELETE FROM` statements in `apply/recurring.rs`:

- `recurring_transfers` at `:93-108`,
- `income_sources` at `:264-278`, and
- `bill_contracts` plus `recurring_events` at `:633-654`.

Those deletes cannot safely resolve against a concurrent edit. SYNC-2b must
tombstone them before the S1 command stream freezes. The five import commands
carry device-local staging references; SYNC-2c must reshape them before they
can be envelopes. `SkipStaged` is a local inbox action and never ships.

## Decision

### 1. Three outcomes and one rule

There are exactly three user-visible dispositions. No financial data is
silently dropped; an idempotent no-op is an **auto** disposition, not a drop.

1. **Auto.** Reapply the envelope on the new base only when its write set is
   untouched and the command still validates. An equal end state or an
   idempotent command is an auto no-op only under that same strict predicate;
   a touched write set queues even when the resulting state would be equal.
2. **Queue-choose.** Preserve both the local envelope and the current-base
   value. The user chooses which scalar or toggle outcome wins; the choice is
   emitted as a new command and the queued command remains audit evidence.
3. **Queue-edit.** Open the existing editor with the envelope's intent
   prefilled. The user repairs a reference or invariant (split sum, category
   cycle, or asset/liability link) on the new base, then submits a new command.

The rule is **auto iff** both predicates hold:

```text
write_set_untouched_since(base_seq)
&& validates_against(the_new_base)
```

If either predicate is false, the whole `correlation_id` group queues. A
causal descendant (`causation_id`) that refers to an entity created by the
queued command queues with it, even if its row-level write set looks
disjoint. A group is never partially applied, silently merged, or discarded.

### 2. The four command shapes

The exhaustive 50-row appendix is generated by
`crates/db-worker/tests/adr_0073_disposition.rs`. The test parses the
`WriteCommand` declaration, requires exactly one mapping per variant, asserts
the shape counts (8 Create, 18 Set, 12 Toggle, 4 Base-dependent), and prints
the table used below. A new variant without a row fails the test before a
SYNC-2 implementation can ship it.

#### Create (10)

Create commands append an entity or balanced posting. They auto-apply only
when the strict predicate holds and all referenced rows are still valid on the
new base. An invalid or deleted reference opens **queue-edit**; the editor
validates the repaired command before it can be submitted. Postings append
rather than overwrite another device's money movement, so valid Creates can
be replayed when their write set is untouched; this is not a semantic merge
for a touched row.

#### Set (18)

The fourteen scalar Sets (`SetCardStatementBalance` and
`SetHouseholdTimezone` included) default to
**queue-choose** when a concurrent value differs or their write set was
touched; an exact no-op is auto only when the strict predicate holds. The
three structural Sets are **queue-edit** when their invariant needs repair;
otherwise they also require the strict predicate before auto-apply:

- `SetSplits` must preserve the transaction sum invariant;
- `MoveCategory` must preserve the category no-cycle invariant; and
- `SetAccountLink` must preserve the real-asset → liability rule.

`SetTags` is replacement-style, not a semantic set-union merge. It is auto only
when the strict predicate holds; if its write set was touched, it is
**queue-choose** with both replacement payloads. Rebase never rewrites a
replacement payload into a union and never removes the other device's evidence.
A balance assertion is still a Set, but it is never LWW: two assertions for
the same account and date always produce **queue-choose** with both values and
dates (ADR 0027; ADR 0074 Decision 5).

#### Toggle (12)

Archive/reinstate, void, unconfirm, snooze, and dismiss commands compare their
end state. Equal end states auto-apply only when the strict predicate holds;
any touched write set—including one with an equal end state—produces
**queue-choose**, as does an opposed state. The three hard deletes are not
Toggle until SYNC-2b replaces them with tombstones; their exception rows are
listed separately below.

#### Base-dependent (4)

These commands must be re-evaluated against the new base rather than treated
as ordinary scalar Sets. Any automatic result still requires the strict
untouched-and-valid predicate:

- `ConfirmObligationEarly` is **auto** after idempotent re-evaluation of
  `(recurring_event_id, scheduled_date)`; it must not post the same occurrence
  twice.
- `ConvertUnexplainedToTransaction` is **auto** after re-reading the latest
  assertion and residual plug. If the residual is gone or the account/reference
  is invalid, the normal validation/queue path applies; it never invents a
  replacement amount.
- `ApplyScenario` and `RevertScenarioApply` are **queue-choose**. The
  `command_id` is ADR 0055's reversal handle and survives rebase, so a
  resolver can choose the competing scenario state without losing the inverse.

### 3. Exceptions before the stream

These rows are deliberately not ordinary shape outcomes:

1. **Tombstone first (3).** `DeleteRecurringTransfer`, `DeleteIncomeSource`,
   and `DeleteRecurringBill` become soft deletes in SYNC-2b. Once tombstoned,
   each has an archive/reinstate Toggle disposition. No purge or compaction
   path may erase the tombstone while an envelope can reference it.
   **Resolved 2026-10-19 (`personal-cfo-egn67`): tombstones, now Toggle; see
   Addendum A.**
2. **Reshape first (4).** `CreateSourceBatch`, `AttachSourceRecord`,
   `UpdateBatchState`, and `CommitStaged` reference device-local staging.
   SYNC-2c materializes the command into class-1 or class-1b artifact data
   before it can enter an envelope; a replica never looks up an origin
   `staged_*` row.
3. **Never ships (1).** `SkipStaged` only changes a local staging/inbox
   decision. The envelope builder rejects it.
4. **Invalid references.** A valid Create is auto, but a missing account,
   category, recurring event, or other referenced row is the generic
   queue-edit path. It is not a silent no-op.
5. **Balance assertions.** They are replicated class-1 intent but never
   last-write-wins; the two-value/date choice is mandatory even if the rows
   otherwise look disjoint.
6. **`AlreadyPresent` (provider transactions).** A replayed `CommitStaged` whose
   content-derived provider-transaction identity is already present is resolved by
   ADR 0074 Addendum B, item 4, not by the touched-write-set rule: equal
   provider-financial fields are a no-op plus a dedupe decision and an audit line
   (no inbox item); differing fields are one **queue-choose** item; a voided or
   tombstoned transaction is a no-op. User-editable fields are never compared or
   overwritten. The same check runs at local commit. This is an exception to the
   strict auto-iff rule for this one identity, not a new `WriteCommand` variant, so
   the generated appendix below is unchanged.

The generated appendix reports the rough planning tally from these paths:
23 strict-auto candidate rows (only when the predicate holds), 16
scalar/Scenario queue-choose rows, 3 structural queue-edit rows plus the
generic invalid-reference Create queue-edit path, 3 tombstone-first rows, 4
reshape-first rows, and 1 never-ships row. The planning shorthand “about 23 /
14 / 4” counts the grouped scenario and generic-reference paths rather than
treating every conditional branch as a separate row; the test output is
authoritative. It must not be read as permission to auto-merge a touched row.

### 4. Correlation-group queueing and audit

The rebase executor evaluates the envelope's complete original metadata. If a
command queues, every causal descendant in the same `correlation_id` queues;
the queue record preserves the original envelope, its command/causation IDs,
and the reason. The replica's append-only operation-log row records
`applied_base_seq` and `rebased_from` (R46). Rebase never reuses a numeric
`op_seq`, never applies a command twice, and never installs a dispatchable
idempotency memo for a queued command.

Every enrolled device surfaces the queued group's age and origin device, and
shows a nag at 24 hours (R45). A group remains visible until the user resolves
it with a new command, or explicitly re-bootstraps; there is no expiry that
could look like a drop.

The two-vault simulator must cover these interleavings:

1. pull-first with an untouched valid envelope (auto);
2. seed-twin bootstrap (replicas never seed; genesis carries seed rows);
3. a queued correlation group visible, with age, on the other device; and
4. a rebase whose audit row records `applied_base_seq` / `rebased_from`.

The exit test is property-based: it generates two devices, random command
streams, and random push interleavings. Canonically ordered class-1 and class-2
rows must converge hash-equal; every non-auto envelope remains queued with its
group, no envelope is lost or applied twice, and connector ingestion cannot
commit past device-local staging without the outbox.

## Consequences

- SYNC-2b owns tombstones before any hard delete can be serialized.
- SYNC-2c owns import materialization and the payload-reference lint; it must
  reject a staging ID or local attachment identity in an envelope.
- SYNC-2 and SYNC-1c use the same auto-iff predicate and correlation closure;
  neither may add a per-table LWW exception.
- S3-2 renders queue-choose as a side-by-side scalar/toggle choice and
  queue-edit using the existing split, category, liability-link, or create
  editors. It shows groups, age, origin, and the R46 audit fields—not isolated
  envelopes.
- The implementation changes no current runtime, schema, or user-visible
  behavior. Until those downstream beads land, this ADR is the binding
  protocol contract for the future Sync stream.

## Rejected alternatives

- **Last-write-wins for ledger mutations.** It can overwrite a valid posting or
  violate a cross-row invariant while appearing conflict-free.
- **Row-level CRDTs.** Ledger intent is not a commutative register; balance,
  split, and reference invariants need domain-aware resolution.
- **Field-level merge for money-moving commands.** Merging fields can create a
  posting combination no user issued and cannot preserve the command's
  provenance.
- **A lease or takeover path.** Offline work must remain possible; lease
  expiry creates a second-writer window and a new recovery UX.
- **Drop as an outcome.** An idempotent no-op is the only automatic absence of
  mutation; financial data is never silently discarded.

- **Semantic tag union during rebase.** `SetTags` is a replacement command, so
  rewriting it into a union would invent intent and hide a concurrent edit.
  A future delta-tag command model may support semantic auto-merge, but it
  requires a separately planned bead and ADR; this contract does not grant it.

## Revisit if

- A new `WriteCommand` shape appears; the exhaustive `#[test]` forces a row
  and a reviewed disposition before it can ship.
- The queue-edit UI proves unusable in dogfood (S3), requiring a new ADR rather
  than an implicit fallback to LWW.
- ADR 0027's balance-assertion semantics change.

## Addendum A — Tombstones landed (2026-10-19, `personal-cfo-egn67`)

SYNC-2b is done in code. `DeleteRecurringTransfer`, `DeleteIncomeSource` and
`DeleteRecurringBill` no longer run a `DELETE`: each sets a nullable `deleted_at`
(schema version 57) to the command's `issued_at`, never the wall clock, and a bill's
tombstone covers its `recurring_events` row and its `bill_contracts` row. Three new
commands, `ReinstateRecurringTransfer`, `ReinstateIncomeSource` and
`ReinstateRecurringBill`, clear the tombstone. Deleting a row that is already
tombstoned, or reinstating one that is not, is an accepted, logged no-op, so the end
state is the same on every device. Tombstoning is distinct from archiving: an archived
income source or bill is hidden and restorable through `Archive*`/`Restore*`, a deleted
one is absent from every reader until reinstated, and the two states are independent.
No purge or compaction path exists.

Consequences for the text above, which is otherwise unchanged and describes the state
before SYNC-2b: the exception "Tombstone first (3)" is resolved and has no rows; the six
commands are **Toggle** with the outcome of every other Toggle, which makes **Toggle 18**,
**Tombstone first 0** and 53 appendix rows; and the rough tally reads 29 strict-auto
candidate rows, 16 scalar/Scenario queue-choose rows, 3 structural queue-edit rows plus
the generic invalid-reference Create path, 0 tombstone-first rows, 4 reshape-first rows
and 1 never-ships row. The generated appendix and the `#[test]` that checks it carry the
new rows; the three `Reinstate*` payloads are additive version 1 payloads.

## Addendum B — The bill-to-loan link (2026-10-25, `personal-cfo-6wk.22`)

The ADR 0035 addendum of the same date lets a recurring bill be **linked** to the loan it pays, so
the forecast counts that obligation once. The link is user data on `recurring_events` (a class-1
table, schema version 59: `linked_loan_account_id`, and `not_payment_of_loan_account_id` for the
user's "No, it's a different bill"). It is changed only by three new commands, each a **Set** with
its own additive version 1 payload (the existing payloads are unchanged, and no field was added to
any of them): `LinkBillToLoan`, `UnlinkBillFromLoan` and `SetBillNotLoanPayment` (a loan to remember
the answer, or none to clear it). That makes **Set 21** and 56 appendix rows; the generated
appendix and its test carry the three rows.

**The dangling-link rule (a deterministic apply rule).** A link must name an active
`loan_liability` account. When a replica applies `LinkBillToLoan` on a base where the loan has been
archived, or is no longer a loan, the command **applies as no link**: the column stays `NULL`, it
never errors and never queues on that ground. Both rows then return to the forecast (the bill and
the loan's own payment), so cash never vanishes and the overlap warning describes the pair again.
The rule is the same on every device, including on rebase, and it is idempotent. It is complete
only because the commands that remove the loan or the bill clear the link **in the same command**:

- `ArchiveAccount` clears every link to the archived loan, so a reinstated loan comes back
  unlinked;
- `ArchiveRecurringBill` and `DeleteRecurringBill` clear the bill's own link, so a link only ever
  sits on an active bill and a restored or reinstated bill comes back unlinked.

These clears are part of those commands' write sets (the write set is a state difference), so they
replicate. **One bill per loan:** applying `LinkBillToLoan` for a loan that another bill is already
linked to is a **queue-choose** (the user picks which bill carries the link); locally it is refused
with an error naming the bill.

**Two consequences for the replica side.** The "applies as no link" rule above is a **contract
for the Sync receiver** (the S3-1 apply step), not something this change can enforce, because no
replica applier exists yet; it must use the same clearing statement the commands use. And
`ArchiveAccount` now **also writes `recurring_events`** (it clears the bills linked to the loan), so
its write set includes those rows and the Toggle rule's "touched write set" predicate applies to
them: a concurrent edit of a linked bill on another device queues the archive rather than letting it
silently undo that edit.

## Addendum C — Deleting a connection is a tombstone (2026-10-27, `personal-cfo-07u`)

SYNC-2a splits a connector connection into a replicated identity (`connector_connections`,
`connector_account_links`, class 1) and device-local secrets (`connector_connection_secrets`,
`connector_link_cursors`, class 3; schema version 60). Forgetting a connection used to run a
hard `DELETE` of its links and row. That is a **fourth** hard delete beyond SYNC-2b's three, and
it cannot be replicated as a delete: a replica applying it would leave its own class-3 secret,
cursor and notice rows pointing at a vanished identity, and ADR 0074 decision 2 step 5 puts a
device whose class-3 reference becomes invalid into `RebaseBlockedLocalState`, never dropping the
row, so every device holding a token for the connection would wedge. So the delete is a tombstone:
it sets `deleted_at` on the identity, the mapping rows stay and are ignored (every reader joins
the live identity), the class-3 foreign keys stay valid, and a device-local cleanup after the
rebase swap scrubs and removes that device's secret, cursors and notice and records an audit
event ("token removed: connection deleted"). A tombstone is final: the id is never reusable and
nothing reinstates a connection (a new connection needs a new setup token and a new id). A refresh
that races a delete on another device writes nothing under the tombstoned identity.

Disposition: when the delete becomes a `WriteCommand` (`personal-cfo-5ymg8` routes the identity and
mapping writes through the command bus), it is a **Toggle**-shaped tombstone with the outcome of
every other tombstone, except that there is no `Reinstate`. Nothing in the generated appendix or
its tally changes in this change, because the connector writes are still raw: the tombstone and
the classification are in force, and replication of the identity and mapping starts when
`personal-cfo-5ymg8` lands.

## Addendum D — The connector identity and mapping are commands (2026-10-30, `personal-cfo-5ymg8.2`)

The four writes Addendum C left raw become `WriteCommand`s, so the identity and the mapping
replicate and survive a rebase: `CreateConnectorConnection` (Create), `UpsertConnectorLink` and
`SetConnectorLinkAccount` (Set), and `DeleteConnectorConnection` (Toggle with no `Reinstate`, the
tombstone of Addendum C). That makes **Create 9**, **Set 23**, **Toggle 19** and 60 appendix rows;
the payloads are additive version 1 payloads. The credential, the refresh watermark and the notice
are class 3 and never in a payload, a log or a write set: this device stores its credential after
the create command, and a delete command also scrubs and removes this device's secret, cursors and
notice (writing the "token removed" audit row keyed by the command) on every device that applies it.

**A race with a delete is an accepted no-op, never a rejection.** A link discovered or a mapping
changed on one device while another device deleted the connection reaches a replica after the
tombstone. Refusing it would be a deterministic apply failure that stops every replica over an
ordinary race, so every command on a tombstoned connection applies as a logged no-op with an empty
write set. An unknown connection is a producer fault (the create precedes it in the log) and is
rejected. A discovery that would change nothing is not issued at all, so a refresh does not log or
sync a no-op.

**Class-3 side effects inside apply: the rule.** Applying a command may touch class-3 (device-local)
state only when all of these hold: (i) it is **idempotent under replay**, because a rebase replays
the command and catch-up can apply it again; (ii) it is **monotone**: it clears or destroys, and
never creates anything a rollback would have to undo; (iii) it **never reads class-3 state to
decide a class-1 write**, so every device writes the same class-1 rows whatever it holds locally.
`DeleteConnectorConnection` follows it: the secret, cursor and notice removals are idempotent and
destroy only, and `had_secret` decides only whether the class-3 audit row is written. That audit
row (`connector.token_removed_connection_deleted`, keyed by the command id) records a destruction
that a rebase never undoes, so it is a **stable** event type for the rebase of the mixed
`audit_events` table (`personal-cfo-bxsbz`), never dropped or re-planned with the replayed
commands. `SetConnectorLinkAccount`'s cursor clearing is the same kind of effect.

## Addendum E — The household record (2026-10-30, `personal-cfo-339`)

Schema version 61 adds three class-1 tables, `households` (one row per vault), `household_members`
and `profiles`, written only by seven additive version 1 commands: `SetHouseholdName`,
`AddHouseholdMember`, `RenameHouseholdMember`, `SetMemberProfile` (Sets, and one Create),
`TransferPrimary` (Base-dependent) and `RemoveHouseholdMember` / `RestoreHouseholdMember` (Toggles
over a `deleted_at` tombstone, never a hard delete). That makes **Create 10**, **Set 26**,
**Toggle 21**, **Base-dependent 5** and 67 appendix rows. **Two roles only: primary and partner.**
The viewer role was dropped by the owner before anything shipped (`personal-cfo-2bxkg.14`, option
C), so `household_members.role` is `CHECK (role IN ('primary', 'partner'))`, `AddHouseholdMember`
always adds a partner and its payload has no role field, and there is no `SetMemberRole` (with one
non-primary role there is nothing to change); no read-only flag is added, and a future advisor seat
is `personal-cfo-2bxkg.17`. `SetHouseholdTimezone` keeps its
payload and its meaning; its write set is now the `households` row instead of the logical
`household` record (vault-format C.13, spec-version 16).

**State-validated commands.** The primary seat has exactly one live holder. `TransferPrimary`
names both members and is validated against STATE (`from` must be the live primary, `to` live and
not primary), so after a rebase a stale `from` is a deterministic rejection at the producer and
never a second primary. `AddHouseholdMember` never touches the primary seat, and
the live primary cannot be removed. Apply validates explicitly first; the partial unique index
`one live primary` is a backstop, and the transfer demotes before it promotes because SQLite checks
a unique index per statement.

**A role is not access control.** `household_members.role` is display and ownership metadata.
Every device in the membership chain holds the epoch key and can issue any command, so Sync does
not enforce a role; nothing may rely on a role for security until an ADR says how it is enforced.

**Seeded rows, deterministic in every column.** The household and the first member are not created
by a command. They are seeded at vault creation, or by the migration for an existing vault, with
ids derived from the vault id and every column a pure function of the vault (its own creation
time, fixed default texts), so two devices that create or migrate the same vault independently
hold byte-identical class-1 rows. The local ids are for local use: they derive from the sync-visible
`vault_id` and must never be sent to the platform service (the platform link is
`platform_household_id` / `platform_member_id`, both null with no account, and no command writes
them yet).

## Addendum F — Balance observations are commands (2026-10-31, `personal-cfo-5ymg8.3`)

The two raw writers of `balance_observations` become `WriteCommand`s: `RecordBalanceAssertion`
(Create; a manual observation with a caller-minted id) and `RecordConnectorBalance` (Set). That
makes **Create 11**, **Set 27**, **Toggle 21**, **Base-dependent 5** and 69 appendix rows.

**Manual assertions are never last-wins.** Two assertions for one account and day are both kept
(the latest by `created_at`, then by `id`, anchors the balance) and a rebase that finds two
queues a choice with both values (ADR 0027; ADR 0074 decision 5).

**Connector readings are an upsert, newest wins.** `RecordConnectorBalance` updates the one
`connector_sync` row of an (account, day) IN PLACE, and only when the command's `issued_at` is
newer than the row's `created_at`; an older command applies as a no-op, so a stale refresh from an
offline device cannot overwrite a newer same-day reading, and the rebase disposition is auto. The
row is never hard-deleted (the old staging DELETE and INSERT are gone), and its id is a content id
of (account, day), identical on every device. It carries **no source record**: a staged source
record is device-local (the table is class 1b and not yet routed through the bus,
`personal-cfo-0g528`), and writing it on one device would fork the row's digest, so provenance
returns when connector source records go through the bus. The producer clamps `observed_at` to the
household's today at its impure boundary; apply refuses a reading dated after the household-local
date of `issued_at`.
