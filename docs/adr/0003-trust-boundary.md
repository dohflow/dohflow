# ADR 0003: Frontend / backend trust boundary

## Context

The architecture (ADR 0001) puts the security boundary inside the desktop app: trusted code is Rust-side, untrusted code is the React WebView and any imported / connector / agent payload. Without explicit rules and code-level enforcement, the WebView can drift toward holding secrets, calling the database directly, or rendering hostile input.

This ADR defines what crosses the boundary, what cannot, and what the consequences are when those rules are violated.

## Decision

The frontend (React + TypeScript WebView) is **presentation only**. Every interaction with financial state, secrets, or external systems goes through **typed Tauri commands**, which dispatch to the Rust **Finance Kernel** (ADR 0006). The frontend never possesses the data classes below.

### What the frontend can never hold

- The vault password, KEK, DEK, or per-attachment content keys.
- The SQLCipher database key.
- Connector / aggregator API tokens (Plaid `access_token`, SimpleFIN tokens, etc.).
- Provider-side OAuth client secrets.
- BYOK API keys for cloud AI (OpenAI / Anthropic / etc.); these are read by the Rust agent broker only.
- File system paths for the vault directory or attachment store.
- Raw rusqlite / sqlx connections.

### What the frontend can hold

- Read-model data fetched through typed Tauri commands (already redacted per the logging policy).
- Display-time derived values (formatted strings, locale-rendered dates).
- UI state (route, form drafts, scroll positions). UI state is **not durable** — it lives in memory only.
- Tauri command results and TanStack Query caches. The cache is cleared on lock.

### How the boundary is enforced

1. **Typed IPC.** Tauri commands are declared with serde-derived Rust types; TypeScript bindings are generated by `cargo tauri` (`personal-cfo-40t`). The frontend never calls `invoke('cmd_name', any)` — only typed wrappers.
2. **Validation lives in Rust.** Zod-on-the-frontend is for UX, not authority. Every command re-validates in Rust (idempotency keys, schema version, vault unlock state, domain invariants).
3. **No raw rusqlite outside the db-worker crate.** Enforced by clippy or a grep test (`personal-cfo-chz` owns this boundary).
4. **CSP locks down the WebView** (`personal-cfo-2rf`): no remote URL navigation in production, no Tauri global exposure, no `eval`, restricted script sources.
5. **OAuth / Link flows open in the system browser**, never in the main WebView (per §2.3 rule). Plaid Link, SimpleFIN, and similar must use a separate, tightly scoped surface.
6. **Untrusted document preview and agent report rendering** use a separate WebView with no IPC write capabilities. Agent reports render from typed structured blocks, never arbitrary HTML or general-purpose Markdown.
7. **Logging redaction CI** (`personal-cfo-zobt`) ensures financial values from the trusted side never reach the untrusted log surface.

### Hostile input handling

These are treated as data, not instructions, throughout the trusted core:

- Imported transaction descriptions, merchant names, memo fields.
- Document text (CSV, OFX, QFX, QIF, paystubs, bank statements).
- LLM responses (schema-validated and safety-checked before any rendering or storage).
- Connector responses.
- User-supplied rule strings.

## Consequences

### Positive

- Compromised WebView cannot read the vault or write financial records.
- Lost / leaked frontend code (e.g., browser DevTools in dev) does not leak secrets.
- Future contributors get a clean, enforceable rule set with code-level checks (clippy + grep + CSP).
- Connector and AI integration paths inherit the boundary instead of carving exceptions.

### Negative

- Every UI interaction that needs new data requires a new Tauri command + serde type + TS binding. This is intentional friction.
- Some UX patterns (e.g., autosaving form drafts) require explicit serialization through commands rather than direct DB access.
- OAuth flows in the system browser are slightly clunkier than embedded webviews, and Plaid has [deprecated webview-based Link integrations](https://plaid.com/docs/link/oauth/) which aligns with this rule.

## Rejected alternatives

### Trusted Node IPC bridge (Electron-style)

- ✗ Node is a poor security boundary.
- ✗ The Tauri capability model gives us a stronger one for free.

### "Frontend can hold tokens, but encrypt them"

- ✗ Encrypted-but-decryptable means the decryption key is in the WebView too. Defeats the point.

### Single-process Rust + Skia/Egui native UI (no WebView)

- ✗ Erases the React ecosystem advantages from ADR 0001.
- ✗ Forces us to rebuild table/grid/chart primitives we get free from the JS world.

### Direct rusqlite calls from a Rust Tauri command, bypassing the Finance Kernel

- ✗ Defeats the kernel's idempotency/audit/atomicity guarantees (ADR 0006). Allowed only via the kernel's typed commands.

## Revisit if

- A specific UX requirement makes the typed-IPC boundary genuinely intractable (we revisit case-by-case rather than weakening the rule).
- We add a multi-process model where the WebView and the kernel run in different processes — the boundary may shift but the rules tighten, not loosen.

## Implementation notes

- The deny-list above is repeated in `docs/architecture/trust-boundaries.md` for human contributors.
- Code review checklist for any new Tauri command: validates in Rust ✓, idempotency where applicable ✓, span emitted ✓, redaction CI passes ✓, no DB call outside db-worker ✓.

## Addendum (2026-07-01): in-app from-source updater (`personal-cfo-1ik.3`)

The dogfooding build is unsigned and built from source; there is no signed-release feed yet
(that is `personal-cfo-867.1`). To let the running app check for and apply updates, a small,
**deliberately scoped** exception to "no network / no external processes" applies to the
**update feature only**:

- The `check_for_update` command (and, in a follow-up, the apply/relaunch commands) runs `git`
  (and, on apply, `scripts/update-app.sh` → `pnpm`/`cargo`) via `std::process::Command` from the
  **trusted Rust side** — never the WebView, and **not** the Tauri shell plugin, so it needs no
  capability grant and does not widen the renderer's surface.
- The **only network** is `git fetch`, performed by `git` using the user's own credentials — the
  WebView's `connect-src 'self'` CSP is **unchanged**; the renderer still makes no external
  requests. So the offline-first guarantee for user data is intact.
- It is a **dev-machine / from-source** mechanism: it needs the source checkout (path stamped at
  build time by `build.rs`) + the toolchain. When absent it degrades to a clear message, never a
  crash. It compares the built commit (`PCFO_GIT_COMMIT`) to the current branch's upstream.
- This does **not** loosen the kernel boundary: updates touch no vault data and go nowhere near
  db-worker; they only rebuild + reinstall the app binary. At real distribution this is replaced
  by the signed/notarized auto-updater (`867.1`), which supersedes this addendum.

## Addendum (2026-09-08): the signed release updater, and where plugin bindings sit on the boundary

**Bead:** `personal-cfo-867.1.2`. ADR 0068 decides the distribution and update
channel; ADR 0010's 2026-09-08 addendum decides the capability grants. This
addendum records what the change means for **this** ADR's boundary, and amends
the 2026-07-01 addendum above.

### The 2026-07-01 addendum is narrowed, not superseded

That addendum said the from-source updater "is replaced by the
signed/notarized auto-updater (`867.1`), which supersedes this addendum." In
practice both mechanisms now ship, chosen by build channel:

- **`PCFO_BUILD_CHANNEL == dev`** — the from-source updater described in the
  2026-07-01 addendum, unchanged and still in force. It remains the only update
  path for a dogfooding build made from a source checkout.
- **Every other channel (release)** — the Tauri updater plugin described below.
  A release build never runs `git`, never shells out to `update-app.sh`, and
  never needs a source checkout.

So the 2026-07-01 addendum stands, scoped to the dev channel.

### Where the boundary actually falls

The renderer calls the updater plugin's JS bindings
(`@tauri-apps/plugin-updater`'s `check()` / `downloadAndInstall()`, and
`@tauri-apps/plugin-process`'s `relaunch()`) directly from
`useSoftwareUpdate.ts`, rather than through the app's own generated-commands IPC
(`ADR 0003`'s typed `commands` surface, `personal-cfo-40t`). That is consistent
with this ADR, and the distinction is worth stating plainly because it recurs:

- **The app's own commands** — anything in `collect_commands!` — are the typed,
  codegen'd surface this ADR governs, deny-by-default through
  `permissions/*.toml`. Nothing changes there.
- **First-party Tauri plugin commands** are a different surface with its own
  enforcement: they are gated by *capability grants* (ADR 0010), and the plugin
  validates its own inputs in Rust. The renderer can only reach what the
  capability allows. The app already relies on this for
  `@tauri-apps/plugin-dialog` (backup export/restore) and
  `@tauri-apps/plugin-opener` (the About card's links); the updater is the same
  pattern, not a new one.

**What crosses to the trusted side is what matters here, and all of it does:**
the HTTPS fetch of `latest.json` and the artifact, the **minisign signature
verification against `tauri.conf.json`'s committed `pubkey`**, and the install
that replaces the app bundle all happen in Rust inside the plugin. The renderer
initiates and observes; it never handles the bytes, never verifies the
signature, and cannot substitute an endpoint (the endpoint is pinned in the
committed config, not passed from JS).

### What is unchanged

- **The CSP.** `connect-src 'self' ipc: http://ipc.localhost` does not gain the
  GitHub origin, because the renderer makes no external request — exactly as the
  2026-07-01 addendum reasoned for `git fetch`. Pinned by
  `acl_coverage.rs`'s CSP test.
- **The kernel boundary.** Updates touch no vault data and go nowhere near
  db-worker; they replace the app binary only.
- **The offline-first guarantee for user data.** The only network call is an
  unauthenticated `GET` for a public manifest, carrying no identifiers
  (ADR 0068 point 5).
